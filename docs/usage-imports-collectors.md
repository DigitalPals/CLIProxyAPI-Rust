# Collector progress and local storage limits

Authenticated collector batches may include `progress`, an optional array with at most one report for each of `codex` and `claude_code`. Older batches may omit it. The dashboard collector status returns the last committed reports in each collector's `progress` array; it remains empty until a collector reports progress.

Each report contains only `source`, `state`, `imported`, `duplicate`, `skipped`, `unsupported`, `failed`, and `last_scan_at_ms`. Sources and states are strict enums. Counters must be between zero and one trillion. The timestamp may be null or fall between January 2020 and tomorrow; `ready` requires a scan timestamp. Unknown fields, duplicate sources, invalid enum values, and out-of-bound values reject the batch. Reports are committed atomically with observations and supersession, under the authenticated collector identity. They contain no root paths, project names, prompts, transcript text, credentials, or free-form diagnostics.

The standalone collector sums scan counters across configured roots for each source. Counters describe cumulative scan outcomes and may include revisions or replay; they are not unique expenses or amounts of paid subscription usage. `unknown` means there are no configured roots or at least one enabled root has no scan evidence. `disabled` means all configured roots for the source are disabled. `attention` means an enabled root reported an error. `ready` means every enabled root has scan evidence and no current error. These states do not claim that the entire history is known or that backfill is complete. The timestamp is the latest scan recorded for that source. Server reports may be stale while a collector is offline; use the separate contact and committed-sync timestamps to assess freshness.

The local collector database uses SQLite `journal_mode=DELETE` and `synchronous=FULL`. The main server database continues to use WAL. A collector's `max_page_count` limits its database, including schema, saved checkpoints, import configuration, and outbox, to 64 MiB. SQLite may additionally create a temporary rollback journal with approximately one original page image per modified database page. The status reports a conservative 130 MiB budget for the database and rollback journal together; this is not a filesystem quota or a cap on unrelated files in the state directory. The credential JSON is small. The collector does not retain a growing WAL. Startup fails if SQLite cannot switch journal mode, or an existing database exceeds the database limit; existing pending records are preserved.

Local status includes `outbox.storage.database_bytes`, `free_page_bytes`, `database_limit_bytes`, `sqlite_files_budget_bytes`, and `journal_mode`. Its storage state becomes `full` when the page limit is reached without reusable free pages. `collector.state` becomes `paused` when this condition or the existing 10,000-record/16 MiB serialized outbox bound is reached. Existing partially filled pages may still accept some updates; allocation failures can occur earlier if the filesystem is full. Scan errors are also visible in source progress as `attention`.

Failed allocations roll back the current file's outbox/checkpoint transaction; pending records and earlier committed checkpoints remain intact. Scans can resume after successfully delivered records free pages. Acknowledged outbox rows are removed without deleting unsent revisions. SQLite can retain allocated pages for reuse, so successful synchronization does not necessarily shrink the database file. A completely full database may lack space for startup metadata or acknowledgements; in that case a command reports storage failure and retains pending data. Keep the state directory private and persistent, and preserve the database when resolving capacity problems. Do not delete pending outbox rows or raise a progress state to complete to bypass the limit.
